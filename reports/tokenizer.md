# 分词器报告：mt32k

- 文件：`tokenizer/mt32k.json`，指纹 `0a87b9848bf6d598`
- 字节级 BPE，词表 32768（含 16 个特殊 token），数字一位一切
- 训练：1.0 GB 抽样语料，本机 CPU 5.7 分钟，峰值内存约 2 GB
- 代码：`src/mytransformer/tokenizer/`；抽样 `scripts/sample_tokenizer_corpus.py`；评测 `scripts/tokenizer_report.py`
- 原始数字：`reports/tokenizer_eval.json`（和别家对比）、`reports/tokenizer_sweep.json`（词表大小扫描 + 数字切分消融）

**结论**：

1. 对 250M 模型，**32768 是四个候选词表里"每字节文本算力最低"的**（§3）。词表再大，压缩率的提升抵不上 lm_head 多出的计算量
2. **中文压缩率与 Qwen2.5 相当**（0.70 vs 0.65 tokens/字），好于 Llama-3 和 GPT-4o（§2）
3. **英文比大词表分词器多约 7–11% 的 token**（1.45 vs 1.30–1.35 tokens/word）。这是 3.2 万个词表位置要同时分给中文、英文和代码的代价。路线图原定的"英文 ≤ 1.35"在 32k 双语词表下做不到，连 64k 也只到 1.37，验收标准已按实测修改（§5）
4. 数字一位一切让总 token 数多 2.2%（§4）。为了算术保留

**怎么读这两张表**：

- **中文**：mt32k 用 1/5 的词表，做到和 Qwen2.5 相当、比 GPT-4o 和 Llama-3 好。原因是词表里 27%（8830 个）是含汉字的 token，而 GPT-4o、Llama-3 的词表以英文和多语言为主。只见过英文的 GPT-2、SmolLM2 每个汉字要 1.7–2 个 token，基本是在逐字节切

## 3. 为什么是 32768：词表大小扫描

同一份语料、同样的设置，只改词表大小，再用 250M 模型（d=1024，18 层）的实际计算量来衡量。

| 词表 | 混合 bytes/token | 嵌入参数 | 嵌入占总参数 | FLOPs/token | **FLOPs/字节**（相对 32k） |
|---|---:|---:|---:|---:|---:|
| 16,384 | 3.560 | 16.8M | 7.6% | 1.77G | 1.035 |
| **32,768** | 3.894 | 33.6M | 14.2% | 1.87G | **1.000** |
| 49,152 | 4.060 | 50.3M | 19.9% | 1.97G | 1.011 |
| 65,536 | 4.165 | 67.1M | 24.9% | 2.07G | 1.035 |

"混合 bytes/token"按预训练配比（`docs/05-data.md`）对各评测集加权。"FLOPs/字节"= FLOPs/token ÷ bytes/token，即**学同样多的文本要花多少算力**，这才是预算真正关心的量。

- 词表翻倍（16k→32k）压缩率提升 9.4%，词表再翻倍（32k→64k）只提升 7.0%：收益递减
- 每多 16384 个词，lm_head 每个 token 多 6 × 1024 × 16384 ≈ 0.10 GFLOPs（+5%）
- 两者一抵，**32k 是谷底**。48k 只贵 1%，差别在误差范围内；但它会让嵌入占比从 14% 涨到 20%，对这个模型来说是一笔不划算的参数

这个结论只对这个模型规模成立。模型越大，lm_head 在总计算量里的占比越小，最优词表就越大。这也是为什么 7B 以上的模型普遍用 10 万以上的词表。

## 4. 消融：数字一位一切的代价

把预切分里的 `\p{N}` 换回 GPT-4 原版的 `\p{N}{1,3}`，其余完全不变，重新训练：

| | code | en_web | math | zh_web | 混合 bytes/token | FLOPs/字节 |
|---|---:|---:|---:|---:|---:|---:|
| 一位一切（mt32k） | 3.16 | 4.23 | 3.42 | 4.01 | 3.894 | 1.000 |
| 1–3 位一块 | 3.24 | 4.33 | 3.54 | 4.06 | 3.982 | 0.978 |

一位一切让总 token 数多约 2.2%，数学文本多 3.5%。在 mt32k 的编码结果里，单个数字 token 占 en_web 的 5.5%、math 的 12.0%、code 的 7.0%。

**仍然保留一位一切**：多出的 2.2% 算力，换来每个数字永远是同一个 token。按 1–3 位切，"1234" 是 `123|4`，"12345" 是 `123|45`，同一个数字 1 在不同的数里落进完全不同的 token，小模型很难学会进位对齐。LLaMA-1、DeepSeek LLM 等都选择一位一切。本项目后面要评测 GSM8K，这笔代价值得付。

## 5. 对路线图验收标准的修改

原标准是"中文 ≤ 1.7 tokens/字，英文 ≤ 1.35 tokens/word"。实测：

- **中文 0.70**：远好于 1.7。1.7 大约是纯英文分词器（SmolLM2）的水平，这条标准定得太松
- **英文 1.45**：达不到 1.35。§3 的扫描显示，同一份双语语料上连 64k 词表也只到 1.37。1.35 是专门的英文分词器、或 10 万级词表才能达到的水平，这条标准定得没考虑到 32k 词表要中英共享

改为按实测可以守住的标准，用于以后换语料重训时防止退化：**zh_web ≤ 0.75 tokens/字，en_web ≤ 1.50 tokens/word，混合 bytes/token ≥ 3.85**。

## 6. 词表里都有什么

| 类别 | 个数 | 占比 | 例子 |
|---|---:|---:|---|
| 英文字母（可带前导空格） | 20,240 | 61.8% | ` issues`、` importantly`、`elebr` |
| 含汉字 | 8,830 | 26.9% | `发生在`、`地址`、`；而` |
| 标点/符号 | 1,710 | 5.2% | `)：`、`……………………`、`{\n\n` |
| 字母数字与符号混合 | 1,633 | 5.0% | `.getString`、`_instance`、`#include` |
| 其他非 ASCII（西里尔、希腊、带重音拉丁字母） | 206 | 0.6% | `д`、` σ`、`é` |
| 纯空白（代码缩进） | 127 | 0.4% | 长串空格（最长 128 个）、`\t\t\t\t\n` |

- 含汉字的 token：2 字的最多（4614 个），其次是单字（3015），3 字（1020），4 字以上很少。中文的预切分会把一整句连续汉字切成一块，BPE 在块内合并出高频词
- 最长的 token 是代码里的注释分隔线（64 个 `-`、`=`、`*`、`/`）和 128 个空格的缩进
- 有 6 个 token 以不完整的 UTF-8 字节结尾，比如 `ー` 后面跟着下一个片假名的前半个字节。字节级 BPE 允许这种合并，解码时拼起来仍然正确（往返测试覆盖了这一点）
