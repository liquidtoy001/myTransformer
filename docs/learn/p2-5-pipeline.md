# P2-5 把四步串成流水线：2B tokens 实跑

代码：`scripts/build_dataset.py`（约 280 行）、`src/mytransformer/data/sources.py`（约 170 行）
配置：`configs/data/pipeline_2b.yaml`　产出：`data/p5/mix/`（2.000B tokens，20 个分片，3.8 GB）
报告：[reports/data.md](../../reports/data.md)

---

## 1. 它解决什么问题

P2-1 到 P2-4 各自都在几千篇文档上验证过了。这一步要把它们接成一条能跑几小时、能中断、能重来的流水线，并且**把每一步丢了多少记下来**——报告里的漏斗表就是数据可信度的全部依据。

实际用时（本机 24 核，10 个进程）：

| 阶段 | 内容 | 用时 |
|---|---|---:|
| fetch | 下载 + 质量过滤 + MinHash 签名 + 查污染（232 个分片并行） | 45 分钟 |
| tokenize | 分词成 docs.bin | 14 分钟 |
| clean + pack + report | 近似去重（214 万篇，签名 2.2 GB，只要 24 秒）+ 段落去重 + 写分片 + 出报告，全部串行 | 9 分钟 |

读入 11.1 GB 文本、214 万篇文档，最终 2.000B tokens。磁盘峰值约 15 GB（含所有中间文件）。

## 2. 哪些步骤能并行，哪些不能

这是整条流水线的骨架：

| | 能并行吗 | 为什么 |
|---|---|---|
| 质量过滤、MinHash 签名、查评测污染 | **能** | 每篇文档独立判断，互不影响。所以合并成一个阶段（`fetch`），一篇文档只解析一次 |
| 近似去重 | **不能** | 要把所有签名放在一起才能分桶找重复 |
| 段落去重 | **不能** | 规则是"只保留第一次出现"，顺序一变，删掉的就不是同一批了 |

所以 `fetch` 用 10 个进程跑，`clean` 在主进程里按固定顺序走一遍。214 万篇的签名占 2.2 GB 内存，去重只要 24 秒（`near_duplicates` 先用 numpy 挑出至少两篇的桶，再用 Python 遍历，见 P2-2）。

**一个折中**：段落出现在几篇文档里，是在 `fetch` 阶段对"过滤后、去重前"的文档统计的（这样才能并行）。去重又会删掉一些，所以计数略偏高，对"≥3 篇才算常见段落"的判断影响很小。

## 3. 中断了怎么办：任务切分必须是确定的

下载 11 GB 要 45 分钟，中途断网、关机都很正常。做法是把每个阶段切成"分片"，每个分片做完写一个 `.json` 统计文件，重跑时**有统计文件的直接跳过**。

关键在于：**同样的配置必须每次都切出同样的分片**。我在这里连犯了两个错，都是重跑时才暴露的：

**坑 1：估算只探了第一个行组，而且没套过滤规则。**

规划时要估"每个行组能提供多少可用文本"，我一开始读文件的第 0 个行组，直接按文本长度算。结果：

- 代码子集只保留 13 种语言、单文件 ≤100 KB，实际可用的只有估计值的约 40%
- 维基按条目 id 排序，开头几千条和中间的长度差 3 倍

两个子集都取少了。改成**探 3 个分散的行组，并且用这个子集真正的过滤规则过一遍**。

**坑 2：最后一个任务被截断，导致分片编号错位。**

原来的代码是"最后一个任务只取剩下需要的几个行组"。目标量一改，最后一个任务的内容就变了，后面的编号也跟着变——**已经下好的分片会被错误复用**。改成每个任务固定取满 8 个行组（宁可多取一点），任务列表就只和文件顺序有关，改目标量只会在末尾追加任务。

教训：**"能跳过已完成的工作"这个能力，取决于任务划分是不是确定的。** 划分逻辑里任何依赖"总量"的地方都会破坏它。

## 4. 实跑发现的四件事

详见 [reports/data.md](../../reports/data.md) §四，这里挑最有价值的：

**"汉字占比 ≥ 40%"挡下了 8.9 万篇英文。** zh_web 因此丢了 15.4%，但各分片的中位丢弃率只有 0.2%：几乎全部集中在 6 个分片上，它们读的是 `chinese-fineweb-edu-v2` 的 `00312.parquet`，整段都是英文文档（英文医学论文、英文新闻）。**一个"中文数据集"里混着成片的英文**，没有这条规则，它们会占掉中文的配额。

**去重率随规模上升。** 校准时 2000 篇里一篇重复都没有，214 万篇里有 1.86 万篇（0.9%）。小样本上"没发现重复"什么也说明不了。

**跨子集的重复很少：424 篇，占全部重复的 2.3%。** 主要是 fineweb-edu 和 DCLM 之间（317 篇）——两者都来自 Common Crawl。所以"重复时保留哪个子集"的优先级设置，只影响这 424 篇。

**评测污染主要在中文网页上**：zh_web 命中 C-Eval 1566 篇、CMMLU 846 篇（0.5%），en_web 命中 MMLU 272 篇、HellaSwag 52 篇（0.03%）。

## 5. 怎么读代码

**顺序**：`configs/data/pipeline_2b.yaml`（要什么）→ `sources.py` 的 `plan_tasks`（去哪读）→ `build_dataset.py` 的 `_fetch_one`（每篇文档做什么）→ `stage_clean`（全局的两件事）→ `stage_tokenize`、`stage_pack`（P2-4）→ `stage_report`。

配置里三个数决定下载量：目标 token 数 × `bytes_per_token`（P1 实测的压缩率）× `loss_factor`（过滤损耗的余量 1.35）。

## 6. 怎么验证它是对的

```bash
python scripts/build_dataset.py --config configs/data/pipeline_2b.yaml --scale 0.005   # 约 3 分钟
```

`--scale` 把所有目标量按比例缩小，整条链路跑一遍，产出在 `data/p5_scale0.005/`。**改了流水线先用它跑一遍**，比等 45 分钟再发现问题划算得多。

跑完之后：

1. 看 `reports/data.md` 的漏斗表，每一步的保留率是否合理
2. 翻 `data/review_sample.txt`（随机 200 篇），有没有乱码、模板页
3. 用真实分片跑一次短训练，确认能读、指纹核对通过：

```bash
python -m mytransformer.train.pretrain --config configs/train/smoke_p5.yaml   # 60 步，约 1 分钟
```

### 动手练习

| # | 做什么 | 会看到 |
|---|---|---|
| 1 | 删掉 `data/p5_scale0.005/math/raw/part_00000.json`，重跑 `--stages fetch --scale 0.005` | "共 10 个分片，已完成 9"，只重下这一个 |
| 2 | 把配置里 `priority` 的顺序整个颠倒，重跑 `--stages clean --scale 0.005` | **各子集保留数一篇都没变**——这份小样本里没有跨子集重复。全量数据上也只影响 424 篇（§4） |
| 3 | 复制一份配置、把 `total_tokens` 改成 5 倍，用同一份数据重跑 `--stages pack --scale 0.005` | 数据不够配额，`epochs` 从 0.8 涨到 3.8–4.1（en_web 3.79、zh_web 4.08），说明同一批文档被反复用了四遍 |

练习 2 是我本来想用来演示优先级作用的，结果一个数都没变。**这也是结果**：它说明优先级这个设计在这份数据上几乎不起作用，把精力花在别处更值。
