# P2-2 去重：MinHash-LSH 和段落去重

代码：`src/mytransformer/data/dedup.py`（约 190 行）
校准：`scripts/calibrate_dedup.py`（用 P2-1 取下来的真实文档）
测试：`tests/test_dedup.py`

---

## 1. 它解决什么问题

同一篇文章在网上被转载几百次。不去重的话：

- 模型会**背下**这些文章（loss 在它们上面降得特别低，看起来训练很好，其实是记忆）
- 训练预算被白白花在重复内容上
- 评测题如果恰好在重复内容里，分数就是假的（这是 P2-3 的事）

难点是"重复"通常不是逐字相同：转载会加上"【转载】"、改几个字、换个标点。需要**近似**去重。

## 2. 文档级：MinHash-LSH

### 2.1 怎么衡量两篇文档有多像

把文档切成**shingle**：连续 5 个词（中文按连续 5 个字）的集合。两篇文档的相似度用 Jaccard 衡量：

```
J(A, B) = |A ∩ B| / |A ∪ B|
```

改了 2% 的词，J 约 0.8（每改一个词会破坏包含它的 5 个 shingle）；完全无关，J 接近 0。去重前先归一化（小写、去标点、全角转半角），"Hello, World!" 和 "hello world" 算同一段。

### 2.2 MinHash：把集合压成 256 个数

直接比较两个集合很慢，而且 N 篇文档要比 N²/2 对：200 万篇就是 2 万亿次。

MinHash 的做法：准备 256 个不同的哈希函数，对每个函数，记下文档所有 shingle 里**哈希值最小**的那个。这 256 个最小值就是文档的**签名**。

核心性质：**两个签名在同一位置相等的概率，恰好等于 J**。直觉：把两个集合的并集随机打乱，排第一的元素恰好同时属于两个集合的概率就是 |A∩B|/|A∪B|。所以数一数 256 个位置里有几个相等，就能估计 J。`test_signature_estimates_jaccard` 验证的就是这个性质。

### 2.3 LSH：只比较"可能相似"的对

把 256 个数切成 32 段、每段 8 个。**任何一段 8 个数全部相同**的两篇文档才成为候选，拿出来比较。相似度为 J 的一对成为候选的概率是：

```
P = 1 − (1 − J^8)^32
J = 0.8 → 99.7%      J = 0.5 → 12%      J = 0.3 → 0.2%
```

实现上不用两两比较：对每一段，把 N 个"8 个数的组合"排序，相同的挨在一起，一次排序就找到所有候选。

### 2.4 候选还要复核

LSH 只保证"可能相似"：两篇无关的文档碰巧有一段相同，也会成为候选。所以每个候选对再用签名估计一次 J，≥ 0.8 才算重复。

不复核会怎样？在中文维基上实测，精确率从 96% 掉到 **7%**（练习 3）。

### 2.5 为什么用 256 个哈希，不是常见的 128

这是这一篇的核心发现。在中文维基的 2000 篇文档上，**暴力枚举所有 200 万对的真实 J**，得到"理想情况下应该删哪些"，再和 MinHash-LSH 比（6 个随机种子）：

| | 精确率（删的里面真该删的） | 召回率（该删的里面删到的） | 签名速度 |
|---|---:|---:|---:|
| 128 个哈希 / 16 段 | 51–84% | 77–95% | 1× |
| **256 个哈希 / 32 段** | **86–96%** | **89–98%** | 约 0.6× |

原因：中文维基有大量模板条目（"X 是位於美國肯塔基州…的一個非建制地區"），彼此的真实 J 在 0.75 左右，就在阈值 0.8 下面一点。128 个哈希的估计有约 ±0.04 的噪声，几百对 0.75 的文档里，总有一些被噪声推过 0.8。**被判为重复的，恰恰是被高估了的那些**，所以精确率很低。这叫"赢家的诅咒"（winner's curse）：从很多个带噪声的估计里挑出超过阈值的，挑出来的系统性地偏高。

这个问题在英文网页上看不出来（那里几乎没有 J≈0.75 的文档对），只在有大量模板页的来源上暴露。**同一套参数在不同来源上表现可以完全不同**，这和 P2-1 的结论一样。

### 2.6 暴力枚举：又一次"答案已知"的检验

暴力枚举在几百万篇上做不到，但在 2000 篇上只要几十秒。**在小规模上用笨办法算出准确答案，拿来检验聪明办法**，这是验证近似算法的通用方法。

## 3. 段落级：精确去重

整篇不重复，但包含相同段落的情况很多。实测找到的：

| 来源 | 最常见的重复段落 |
|---|---|
| math | GMAT Club 论坛的"we will pick new questions that match your level..."（2000 篇里 35 次） |
| zh_web | "受苹果公司新规定影响，微信 iOS 版的赞赏功能被关闭……"（25 次） |
| en_web_dclm | "blog comments powered by Disqus" |
| en_wiki | 小条目末尾的 "External links" |
| code | Apache 许可证头（39 次）→ **代码不做段落去重** |

做法：两遍扫描。第一遍统计每个段落（按空行切开，≥ 30 字符）出现在几篇文档里；第二遍，出现在 ≥ 3 篇里的段落只在第一次出现的地方保留。

- **只存段落的哈希**，几百万篇文档的统计也放得进内存（`common_paragraphs` 和 `strip_repeated` 分开，就是为了能一边读文件一边处理）
- **短段落不参与**："References"、"参考文献"这类小标题到处都有，删了会破坏文章结构
- **代码不做**：代码里重复的块删掉，文件可能就不完整了

P2-1 里数学没有用"重复行按条数"的规则，理由是论坛界面文字只占全文一小部分。现在段落去重把这些界面文字精确地删掉了，文章本身保留下来，比整篇扔掉更好。

## 4. 怎么读代码

**顺序**：`normalize` → `shingles` → `MinHasher.signature` → `near_duplicates` → 段落部分。

- `MinHasher`：哈希函数是 `(a·x + b) mod (2^61 − 1)`。x 是 shingle 的 crc32，a、b 都限制在 32 位以内，这样 `a·x + b < 2^64`，numpy 的 uint64 **不会悄悄溢出**（numpy 整数溢出不报错）
- **不能用 Python 自带的 `hash()`**：它对字符串加了随机盐，每次启动 Python 结果都不同。同一个进程里看不出问题，分多个进程跑去重时签名就对不上了。`test_signature_is_deterministic_across_processes` 专门另起一个进程来抓这个
- `near_duplicates`：签名矩阵的**行顺序就是优先级**，重复簇里下标最小的保留。P2-5 会把优先保留的来源（比如百科）排在前面
- 并查集（`_find`）把"A≈B、B≈C"连成一个簇

## 5. 怎么验证它是对的

```bash
pytest tests/test_dedup.py
python scripts/calibrate_dedup.py --pr zh_wiki     # 约 30 秒
```

| 测试 | 证明了什么 |
|---|---|
| `test_signature_estimates_jaccard` | 签名估计的 J 和真实 J 相差 < 0.1（改 0%–100% 的词各测一次） |
| `test_signature_is_deterministic_across_processes` | 另一个进程算出的签名完全一样 |
| `test_lsh_curve` | J=0.8 几乎必成候选，J=0.3 几乎必不成 |
| `test_near_duplicates_found_and_lowest_index_kept` | 改 2% 的词、只改大小写标点 → 重复；改一半 → 不重复；保留下标小的 |
| `test_chinese_near_duplicate_by_char` | 加了"【转载】"和"（来源：网络）"的中文转载 → 重复 |
| `test_bucket_collision_is_not_a_duplicate` | 碰巧有一段相同的两篇无关文档，经复核排除 |
| `test_paragraph_dedup_*` | 出现 3 篇删、2 篇不删；短标题不删；删完段落结构不变 |

## 6. 下次怎么自己搭

1. 先写 `shingles` 和 `jaccard`，用暴力两两比较在 100 篇文档上找重复。这是"标准答案"
2. 写 MinHash，验证签名估计的 J ≈ 真实 J
3. 加 LSH 分桶，和第 1 步的暴力结果比精确率和召回率
4. 换一个有模板页的来源再比一次（中文维基），看参数是否还合适
5. 最后写段落去重

### 故意改错练习

规矩见 [README](README.md)。以下都实际跑过。

| # | 改哪里（`dedup.py`） | 结果 |
|---|---|---|
| 1 | `signature` 里 `zlib.crc32(s.encode("utf-8")) for s in sh` 改成 `hash(s) & 0xFFFFFFFF for s in sh` | `test_signature_is_deterministic_across_processes` 失败。同一进程里的测试全部通过 |
| 2 | `parent[max(ri, rj)] = min(ri, rj)` 改成 `parent[min(ri, rj)] = max(ri, rj)` | `test_near_duplicates_found_and_lowest_index_kept`、`test_chinese_near_duplicate_by_char` 失败：保留的变成了下标大的 |
| 3 | `if estimated_jaccard(sigs[i], sigs[j]) >= threshold:` 改成 `if True:` | `test_bucket_collision_is_not_a_duplicate` 失败。再跑 `calibrate_dedup.py --pr zh_wiki`：删 776 篇，精确率 7% |
| 4 | `normalize` 里去掉 `.lower()` | `test_normalize_...`、`test_near_duplicates_...` 失败 |
| 5 | `paragraph_dedup` 的默认值 `min_docs: int = 3` 改成 `2` | `test_paragraph_dedup_threshold[2-0]` 失败 |

**练习 3 的来历**：这个测试是做练习时才加的。一开始的单元测试在"不复核"时全部通过，只有校准脚本看得出精确率崩了。发现以后，手工构造了一对"碰巧有一段相同"的签名，把这个情形固定成测试。**练习发现测试的漏洞，就把漏洞补上**。

另外试过把 `a`、`b` 的范围放大到 61 位（乘法会在 uint64 里悄悄溢出），测试照样全通过，召回率从 96% 变成 89%。但换几个随机种子，不溢出时召回率本身就在 89–98% 之间波动，2000 篇里只有 56 篇该删，样本太小，**分不出是溢出的影响还是随机波动**，所以没有把它列成练习。得出结论之前，先看看噪声有多大。
