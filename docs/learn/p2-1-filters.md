# P2-1 质量过滤：规则怎么定、怎么知道定对了

代码：`src/mytransformer/data/filters.py`（约 200 行）
校准：`scripts/calibrate_filters.py`
测试：`tests/test_filters.py`

---

## 1. 它解决什么问题

网页语料里混着大量不该学的东西：导航栏和页脚、同一句话复制几十遍的 SEO 页、全是列表的目录页、乱码、压缩成一行的 JS。模型会**一字不差地学会这些**，因为它们重复得多、很好预测，loss 降得快。

质量过滤就是在训练前把这些文档扔掉。每条规则都很简单（"平均词长在 3–10 之间"），难的是**定阈值**：定严了会把好文章一起扔掉，定松了等于没过滤。

## 2. 这一篇最重要的一件事：用真实数据校准

我一开始照着 Gopher 论文写了规则，在手写的例子上都对。然后在真实文档上一跑：

| 来源 | 第一版保留率 | 被丢的文档实际长什么样 |
|---|---:|---|
| en_web（fineweb-edu） | 96.2% | 讲资产负债表、学校晨会的正常文章 |
| zh_web（chinese-fineweb-edu） | **40.0%** | 安全作业指导书、会议报道，都是正常内容 |
| math（finemath） | 90.2% | 论坛上的数学问答 |

**怎么判断是规则错了而不是数据差**：fineweb-edu 的作者**已经用 Gopher 规则过滤过一遍**，同样的规则再跑一遍应该几乎什么都不丢。丢了 3.8%，说明我的实现和他们的不一样。

对照 datatrove（FineWeb 用的库）的实现，找到两处差别：

1. **分母**：他们除以整篇文本的字符数（含空格），我除以词的字符数之和（不含空格），比例被放大了约 20%
2. **重复 n-gram 怎么数**：他们找到一个重复就**跳过这 n 个词**再继续；我每个位置都算，重叠部分被数了好几次

改成一样之后，en_web 保留 99.2%。剩下的 0.8% 我没有逐条核对原因，可能来自切词方式的差异（datatrove 用 NLTK 切词，标点单独算一个词），看了样本都是边界情况，可以接受。

**这是这一篇最想让你记住的方法：找一份"答案已知"的数据来检验实现。** 已经被同样规则过滤过的数据，再过滤一遍，结果应该接近零。

### 中文：规则不能照搬

Gopher 的阈值是给英文"词"定的。中文没有空格，我把每个字当一个"词"：第一版（实现还没对齐 datatrove）丢了 60%，对齐之后仍然丢 22%。问题在于一个中文词常常就有 2–4 个字，"按 5 个字算的 n-gram"比"5 个英文词"短得多，常用词组、反复出现的术语这些自然的短重复累计起来就超标了。

把 n 放大，只看重复度规则的丢弃率：

| n 的倍数 | 5-gram 实际是几个字 | 丢弃率 |
|---:|---:|---:|
| ×1 | 5 | 22.0% |
| ×2 | 10 | 6.0% |
| **×3** | 15 | **3.8%** |

选 ×3 的依据不是这个数字本身，而是**看了 ×3 时被丢的文档**：重复占全文 65%、67% 的那种，确实是同一段话抄了好几遍。FineWeb-2 做多语言时也遇到同样的问题，他们的做法是给每种语言单独校准阈值。

### 数学：论坛页的 "Reply"

finemath 里有很多论坛页，"Reply"、"Posts: 2"、"Joined:" 这类界面文字每页重复几十次。"重复行占行数 30% 以上"这条规则会把它们扔掉，但这些短行只占全文很小一部分，数学内容本身是好的。所以数学只用"重复行占**字符** 20% 以上"这一条（`by_count=False`）。

### 最终结果

```bash
python scripts/calibrate_filters.py --fetch    # 第一次，约 1 分钟
python scripts/calibrate_filters.py            # 改了规则之后
```

| 来源 | 保留 | 主要丢弃原因 |
|---|---:|---|
| en_web | 99.2% | 省略号结尾的行过多 0.4% |
| en_web_dclm | 98.0% | 太短 0.7%、省略号 0.6% |
| zh_web | 95.2% | 重复 5-gram 1.7%、汉字不到 40% 1.4% |
| zh_wiki | 86.8% | 太短（< 100 字）12.9%：大量只有一句话的小条目 |
| en_wiki | 98.4% | 太短 1.1% |
| code | 96.7% | 自动生成的文件 2.8%（主要是 javadoc 生成的 HTML） |
| math | 94.7% | 重复行（按字符）3.5% |

## 3. 怎么读代码

**顺序**：`apply()` 和 `FILTERS` 表 → `english()` → `repetition()` → `chinese()` → `code()`、`light()`。

- 每条规则**返回丢弃原因字符串**，保留返回 `None`。这样统计时能知道每条规则各丢了多少，报告里的过滤漏斗表就从这里来
- `repetition()` 顶部的注释写了和 datatrove 保持一致的两个细节，这是最容易写错的地方
- `FILTERS` 按子集选规则。`test_every_subset_has_a_filter` 保证抽样脚本里的每个来源都有规则
- **没做的**：语言识别和困惑度/分类器过滤。选用的来源都已经由原作者做过，重复做只会花时间，还可能因为模型不同而和原作者的判断打架

## 4. 怎么验证它是对的

两层验证，各管一件事：

| | 管什么 | 怎么跑 |
|---|---|---|
| `tests/test_filters.py` | 每条规则的**行为**：该拦的拦住，典型的误杀情形不再发生 | `pytest tests/test_filters.py` |
| `scripts/calibrate_filters.py` | **阈值**在真实数据上是否合理 | 看保留率，再用 `--show 来源名` 看被丢的样本 |

有些性质只能在真实数据上测。比如中文 n×1 和 n×3 的差别来自长文章里成百上千处自然的短重复，手写的小例子复现不出来（下面练习 3 会亲眼看到）。

## 5. 下次怎么自己搭

1. **先写校准脚本，再写规则。** 取每个来源几千篇真实文档，能打印"每条规则丢了多少 + 被丢的样本"
2. 从一条规则开始（比如"太短"），跑校准，看被丢的样本
3. 每加一条规则都重跑一次校准。**丢弃率突然跳高，先看样本**
4. 对"已经过滤过的数据"，丢弃率应该接近零，用它来检验实现
5. 规则稳定后，把校准时发现的典型误杀情形写成单元测试

### 故意改错练习

规矩见 [README](README.md)。以下每条都实际跑过；练习 1–3 另外跑了 `python scripts/calibrate_filters.py`（需要先 `--fetch` 过）。

| # | 改哪里（`filters.py`） | 单元测试 | 校准脚本 |
|---|---|---|---|
| 1 | `_dup_ngram_chars` 里 `i += n` 改成 `i += 1`（不跳过） | `test_dup_ngram_skips_after_a_match` 失败 | en_web 保留 99.2% → 94.0%，zh_web 95.2% → 78.8% |
| 2 | 重复 n-gram 那一行的分母 `text_len` 改成 `max(1, sum(map(len, tokens)))` | **全部通过** | en_web 99.2% → 98.9%；zh_web 不变（中文没有空格，两个分母几乎一样） |
| 3 | `chinese()` 里 `n_scale=3` 改成 `n_scale=1` | **全部通过** | zh_web 95.2% → 77.9% |
| 4 | `"math"` 那行 `by_count=False` 改成 `True` | `test_math_ignores_many_short_repeated_ui_lines` 失败 | — |
| 5 | `chinese()` 里汉字占比那行改成 `if False:` | `test_chinese_rejects` 失败 | — |

**练习 2、3 值得多想**：单元测试全绿，但真实数据上的丢弃率变了，练习 3 变了 17 个百分点。单元测试守护的是"行为"，守护不了"阈值在真实数据上是否合理"，后者只能靠校准脚本，而且要**人去看**被丢的样本。

练习 2 还说明，"比例被放大约 20%"只在阈值附近的文档上才有影响。第一版的 3.8% 误杀是两处差别加在一起的结果，其中"不跳过"影响大得多（练习 1）。
