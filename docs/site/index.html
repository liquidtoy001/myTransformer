myTransformer 是一个学习项目：从零实现一个 decoder-only Transformer，亲手走完分词器、数据、模型、预训练、后训练、评测和报告的整条流程。本文档汇总到 2026-10-05 为止的过程、结果、对后续阶段的预期和优化计划。

目标

  • 完整流程：不调用现成的训练框架，从 BPE 分词器到对话模型，每一步都自己写、自己验证。
  • 一个能用的小模型：250M 参数的中英双语 base 模型，再做 SFT 和 DPO 得到对话模型。
  • 学会做实验：用消融和缩放律做决定，而不是凭感觉选超参数。每个结论都要和随机种子的噪声比较。
  • 学得会：每完成一部分都写一份学习笔记（docs/learn/），讲清楚怎么读代码、怎么验证、下次怎么自己从零搭。

已完成的部分

P1 分词器

自己训练的 byte-level BPE 分词器 mt32k，词表 32768。中文压缩率与 Qwen2.5 相当，英文比大词表分词器多 7–11% 的 token，这是一张 3.2 万词表要同时分给中文、英文和代码的代价。

词表
32,76832 × 1024
中文
0.697token / 字（zh_web）
英文
1.447token / 词（en_web）
混合
3.894字节 / token

设计要点

  • byte-level：任何字节序列都能编码，不会出现未知字符。
  • 数字一位一切：每个数字永远是同一个 token，便于小模型学会进位对齐，代价是总 token 数多 2.2%。
  • 特殊 token 不从文本里解析：网页里出现 <|endoftext|> 这样的字符串，也只会被当作普通文本编码。
  • 指纹 0a87b9848bf6d598：训练时核对数据是不是用同一个分词器打包的。

为什么选 32768

词表越大，压缩率越高，但 lm_head 和嵌入层的计算量也越大。对 250M 模型，真正该比的是"处理每个字节的文本要多少算力"：

词表字节/token嵌入占比FLOPs/tokenFLOPs/字节
16,3843.5607.6%1.77G1.035
32,7683.89414.2%1.87G1.000
49,1524.06019.9%1.97G1.011
65,5364.16524.9%2.07G1.035

FLOPs/字节以 32k 为 1。32k 在四个候选里最低：再大，压缩率的提升抵不上多出的计算量。

验收标准按实测修改

修改

原定"英文 ≤ 1.35 token/词"在 32k 双语词表下做不到，64k 也只到 1.37。验收改为 zh_web ≤ 0.75、en_web ≤ 1.50、混合字节/token ≥ 3.85，实测 0.697 / 1.447 / 3.894，全部通过。

流水线

  1. 下载先探测每个数据集的 3 个 row group，套用过滤规则估出"实际能留下多少"，再按目标 token 数规划下载量。每个任务固定处理 8 个 row group，作业可以随时中断、增量重跑。
  2. 质量过滤英文网页用对齐 datatrove 语义的 Gopher 规则；中文的 n-gram 阈值按字数 ×3 换算，并要求汉字占比 ≥ 40%；数学不按篇数判重复行；代码用 StarCoder 的规则（自动生成文件、超长行）。
  3. 去重MinHash-LSH，256 个哈希、32 个 band；再做段落级去重（代码除外）。跨子集重复时按"百科 > 数学、代码 > 网页"保留一份。
  4. 去污染对 11 个评测集建 13-gram 索引，命中就丢整篇。汉字权重 0.5，并排除 220 个常见 n-gram，降低中文误报。
  5. 分词打包用 mt32k 编码，按配比用"欠额优先"的混合器交错写入 20 个分片，另留每个子集约 1M tokens 的验证集。

每一步都用"答案已知"的数据检验

过滤器、去重、去污染写错了不会报错，只会悄悄丢掉好数据或放过坏数据。所以每一步都先在结果已知的样本上校准：

环节发现的问题修复后
质量过滤fineweb-edu 本身已经过滤过，却只有 3.8% 能通过：规则的语义和 datatrove 不一致对齐 datatrove 语义后保留 99.2%
去重用构造的近似重复对测召回：128 个哈希只找回 51–84%改成 256 个哈希、32 个 band，召回 86–96%
去污染中文网页被误判为污染的约 9%，大多是命中了常见短语汉字权重 0.5，加 220 个排除 n-gram
下载规划代码和维基下载量不够，最后一个任务被截断探测时套用过滤规则，任务大小固定

几个发现

  • 中文数据集里混着 8.9 万篇英文。zh_web 有 15.4% 的文档因为汉字占比不足被丢，几乎全部来自同一个 parquet 文件（00312.parquet）。没有这条规则，这些英文会占掉中文的配额。
  • 去重率随规模上升。校准时 2000 篇里找不到重复，214 万篇里找到 1.86 万篇。小样本上"没有重复"说明不了问题。
  • 评测污染集中在中文网页。zh_web 命中 C-Eval 1566 篇、CMMLU 846 篇；en_web 命中 MMLU 272 篇、HellaSwag 52 篇。C-Eval 和 CMMLU 分别有 27% 和 38% 的题目太短、进不了索引，真实污染率应当更高。
  • 跨子集重复只有 424 篇，其中 317 篇在 fineweb-edu 与 DCLM 之间（两者都来自 Common Crawl）。

已完成的部分

P3 模型实现

LLaMA 风格的 decoder-only Transformer，从零实现，和 HuggingFace 的实现逐位对比，最大误差 8.9e-8。同一份代码通过配置文件切换出缩放实验的三个小模型和各组消融。

结构

  • RMSNorm 前置归一化
  • RoPE 旋转位置编码（θ = 10000，退火期计划改为 500000）
  • SwiGLU 前馈层
  • GQA 分组查询注意力，用 PyTorch 的 SDPA 计算
  • 输入嵌入与输出层共享权重

怎么证明实现是对的

把同一组权重分别载入自己的模型和 HuggingFace transformers 的 LLaMA 实现，输入同一批 token 比较 logits，最大绝对误差 8.9e-8，比验收阈值好 3 个数量级。这个测试能同时查出 RoPE 的维度排列、GQA 的头分组、RMSNorm 的 eps 位置这类"能跑但不对"的错误。

已完成的部分

P4 训练框架

单卡训练器，为 Rangpur 的限制专门设计：作业随时可能被中断，home 空间很小，一次只能跑一个作业。下面每一项都在真实作业里用过。

功能

功能解决什么问题
分块交叉熵32768 维词表的 logits 不一次性展开，按块计算，反向时重算每块 logits。一个 4×2048 的微批上，loss 部分的峰值显存 3.32 GiB → 0.72 GiB
接力续训作业到时前收到 SIGUSR1，立刻存 checkpoint 退出；下一个作业从同一步接着跑，数据加载器也能恢复到原位置
续训自检存档时记下模型对固定输入的输出和下一个 batch 的开头；恢复后重算一遍，对不上就报错。优化器个数变了、训完压缩后又调大 max_steps，也会拒绝续训
原子存档先写临时文件再改名，作业在写到一半时被杀也不会留下坏的 checkpoint
最终评测与瘦身训完自动做完整的验证集评测，只保留权重存为 final.pt：470 MB → 157 MB
数据核对启动时比对分词器指纹和分片大小，防止拿错数据训练
分子集验证验证集按子集分开算 loss，总 val loss 取 7 个子集的等权平均
多优化器Muon 负责二维权重矩阵，AdamW 负责嵌入和归一化参数，各自有学习率

P5 实验

实验设计

P5 回答两个问题：哪些设计选择真的有用（消融），以及 250M 模型大概能训到多少 loss（缩放律）。已完成实验在 Rangpur 单张 A100 上执行；当前 Rangpur 项目目录已备份并清理。

三条规则

  1. 先量噪声。同一配置换 3 个随机种子，得到 val loss 的标准差 σ = 0.0041。差异小于 2σ（0.0081）的不下结论。
  2. 一次只改一处。每个消融配置和底座只允许差一个字段，由单元测试强制检查，写错配置在提交前就会失败。
  3. 训练量相同。消融之间的 token 预算完全一样，否则比的是谁训得久。

def test_ablation_changes_exactly_one_thing(name):

为什么要第二轮

缩放诊断发现，第一轮用的"每步 52 万 tokens"对 39M 模型来说步数偏少（见 缩放律）。第一轮的消融是同条件下的相对比较，方向大概率不变，但幅度可能被夸大，尤其是 Muon：它的优势在大 batch、少步数时最明显。第二轮把 batch 减半、步数翻倍，其余不变，检验结论是否还在；同时补上第一轮缺的 A7（QK-Norm 且保留 z-loss），这是 P6 打算用的组合。

P5 实验

消融结果

第一轮 6 组消融全部超过了 2σ 的噪声线。但超过噪声只说明差异不是随机种子造成的，不说明实验设计没有偏差。逐条看，只有 A2 是干净的结论。

噪声

意外发现：z-loss 让训练慢了 43%

A6 每步只要 1.66 秒，同规模的其他实验都是 3.42 秒左右。QK-Norm 不可能让训练变快，于是在本机同一张卡上只切换两个开关测速：

关开（基线）729 ms6.56 GiB

原实现先算一次交叉熵，再单独算一次 logsumexp，在 32768 维词表上把 softmax 算了两遍。交叉熵 = logsumexp − 正确答案的 logit，所以可以直接复用：

# src/mytransformer/model/transformer.py
mask = y != -100
ce = F.cross_entropy(logits, y, ignore_index=-100, reduction="none")
target = logits.gather(-1, y.clamp_min(0).unsqueeze(-1)).squeeze(-1)
lse = ce + target                         # 不再单独调用 logsumexp
return ce.sum() + z_loss * lse[mask].pow(2).sum()

本机开销从 43% 降到 11%，数值完全一致。Rangpur 上 s2 规模每 52 万 tokens 从 3.37 秒降到 2.53 秒，快了 33%（MFU 16.8% → 22.3%）。A6 和 A5 在同一个节点上跑，剩下的速度差来自编译后的计算路径，不能仅凭这些日志完全排除运行环境的影响。

P5 实验

缩放律

用 3 个小模型的 loss 外推 250M 能训到多少。第一次拟合给出 2.27 到 2.94 的范围，没法用；查下去发现是实验设计让小模型步数不够。按新规则重训后，最佳估计是 250M ≈ 2.74。

第一次拟合为什么不能用

三个点共用每步 52 万 tokens 的 batch 和 100 步 warmup，看起来条件相同。但 s1 总共只有 360 步，warmup 占了 28%，真正用峰值学习率训练的只有六成；s3 有 2836 步，warmup 只占 3.5%。小模型被"步数不够"拖了后腿，曲线被硬掰弯。

诊断方法：同样的模型、同样的 token 数，只把 batch 缩小、warmup 改成总步数的 5%。

模型旧：batch / 步数 / warmup旧 loss新：batch / 步数 / warmup新 loss差

s2512k / 860 / 12%3.6645256k / 1720 / 5%3.5302−0.134

模型越小，固定大 batch 造成的伤害越大。s1 在完全相同的 token 数下，只因为步数够了，loss 就降了 0.91。

新规则下的拟合

横轴是非嵌入参数（对数刻度），纵轴是训完的 val loss。每个点训练 20 tokens/非嵌入参数。

旧规则（空心）新规则与拟合曲线（虚线为外推）250M 外推值

局限

三个点拟三个参数，残差必然为 0，这本身什么也证明不了。这只是三个点的探索性外推，不是置信区间；需要 P6 第四个点检验。

预测的前提

  1. 训练 20 tokens/非嵌入参数，即 4.06B tokens，衰减段占 10%。
  2. 数据是 v1 配比。P6 用 v2，A4 在小模型上有改善，但不能把约 0.05 的收益直接外推到主模型。
  3. 验证集相同：各子集 1M tokens，7 个子集等权平均。

中途对比会夸大最终差距

在同样 token 数、恒定学习率时比较，s2 新旧差 0.26、s3 差 0.20；训完之后只差 0.13 和 0.05。大 batch 的一方在最后的学习率衰减里追回了很多。中途对比能判断"有没有问题"，不能估计"问题有多大"。

经验

教训

P1 到 P5 里最值得记住的四条。它们都不是具体的 bug，而是做实验时的判断方法。

超过噪声，不等于结论可靠

6 组消融全部超过 2σ，但逐条看，只有 A2 是干净的。A1 和 A5 和学习率纠缠在一起，A3 多了参数，A4 是取舍，A6 同时改了两处。种子方差只衡量随机性，衡量不了实验设计本身的偏差。

"条件相同"不等于公平

缩放实验固定 batch 和 warmup 步数，看起来条件相同，实际上对小模型极不公平：它的步数最少，warmup 占比最大。s1 只因为步数够了，loss 就降了 0.91。比较不同规模时，要让每个点的"训练充分程度"一致。

用答案已知的数据检验实现

过滤器、去重、去污染、z-loss 写错都不会报错。能发现问题，靠的是先找一份结果已知的数据：已经清洗过的数据应该大部分通过；构造的重复对应该被找回；关掉一个"几乎零成本"的开关不应该快一倍。

中途对比会夸大最终差距

同样 token 数时 s2 差 0.26，训完只差 0.13。用中途结果判断"有没有问题"可以，用来估计"问题有多大"不行。这也是为什么第二轮消融要完整训到底。
