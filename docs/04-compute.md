# 算力、时间与成本

---

## 一、先把账算清楚

**训练总 FLOPs**（代码里的唯一实现是 `ModelConfig.flops_per_token()`，文档里所有耗时和成本都从它算）：

```
C = (6·N + 6·d·V + 12·L·T·d) · D
     N = 非嵌入参数量          D = 训练 token 数
     d = d_model  V = 词表  L = 层数  T = 序列长度
     6·N       = 各层矩阵乘（前向 2 + 反向 4）
     6·d·V     = lm_head 的矩阵乘
     12·L·T·d  = 注意力打分（QKᵀ 与 AV）
```

后两项常被漏掉，而且**模型越小，漏得越多**：

| | 6N | lm_head | 注意力 | 只算 6N 会低估 |
|---|---|---|---|---|
| S1（非嵌入 9.4M） | 57M | 76M | 57M | **70%** |
| S3（非嵌入 74.3M） | 446M | 151M | 227M | 46% |
| **主线 250M** | 1.218G | 0.201G | 0.453G | **35%** |

lm_head 容易漏的原因：权重绑定后，它的参数被记作"嵌入"，从 N 里扣掉了，但那次 `d×V` 的矩阵乘每个 token 都真实发生。

主线 250M：**每 token 1.872 GFLOPs × 9.437B tokens = 1.767e19 FLOPs**。

9.437B tokens ≈ **40 tokens/param**，是 Chinchilla 最优（20）的 2 倍，属于适度 over-train。

**换算成时间**：`时间 = C / (GPU数 × 峰值FLOPS × MFU)`

| 情形 | MFU |
|---|---|
| 第一次跑，没调优 | 15–25% |
| 单卡 + 常规调优（A100 / H100） | 30–40% |
| 8 卡跑**小模型**（本项目 P6） | **20–28%** |
| 8 卡跑大模型 + 深度优化 | 45–60% |

**小模型在多卡上 MFU 天然偏低**——单卡算力太强、模型太小，通信和边角开销占比上升。下面 8 卡按 25%、单卡 H100 按 30%、A100 按 35% 估。

## 四、性价比：每美元买到多少算力

单价便宜 ≠ 划算。把 MFU 算进去，看**每美元买到多少有效 FLOPs**：

| 硬件 | 单价/卡/时 | 有效算力（含 MFU） | **FLOPs / 美元** |
|---|---|---|---|
| ★ **H100 竞价** | ~$1.5 | 3.96e14 | **9.5e17** |
| RTX 4090（AutoDL ¥2.2） | $0.31 | 5.78e13 | 6.7e17 |
| L40S | ~$0.9 | 1.45e14 | 5.8e17 |
| H100 按需 | ~$2.5 | 3.96e14 | 5.7e17 |
| A100 80G（AutoDL ¥8） | $1.13 | 1.31e14 | 4.2e17 |

**反直觉但重要的结论：租 4090 不比 H100 竞价划算。** 4090 便宜在单价，每美元算力反而低 30%，而且 wall-clock 慢得多（250M×9.44B：8×H100 2.5 小时 vs 单卡 4090 3.9 天）。

消费级卡的正确用途是 **P0–P4 的调试阶段**——那时你要的是"随时能开、开着不心疼、想改就改"，不是吞吐。你本地那张 4070 Ti SUPER 正好胜任，且免费。

**P5 用 Rangpur 的 A100（免费），P6 用 8×H100 竞价。**

### 三个把成本压下来的做法

**1. 缩放律第 4 个点用 WSD 分叉拿。**
P6 训练到 step 9021（= 4.73B tokens = 20 tokens/param）时，分叉出一支做 900 步衰减到 0，得到与 S1/S2/S3 可比的 250M 数据点。**$1.5 而不是重训一次的 $15。**

这正是选 WSD 而非 cosine 的理由在实际中兑现：稳定段 LR 恒定，可以在任意点分叉做退火，不用重训。

> **不能直接拿 P6 在 4.73B 处的中间 checkpoint 当作这个点**。那时 LR 还停在稳定段没衰减，loss 明显高于一个真正训练到 4.73B 就收尾的模型，两者不可比。必须真的做那段衰减。
>
> 这个点在 H100 上、前三个点在 A100 上，**跨了硬件**。val loss 属于质量指标，跨硬件可比（硬件引起的差异小于 seed 方差），前提是**全局 batch 在两边都严格为 524288 tokens**。报告里注明。

**2. 除 P6 外全部放 Rangpur。** P5、P7、P8 免费；存储上 P5 只需 4 GB 数据，放得进 home（见 [09-rangpur.md](09-rangpur.md) §三）。

**3. P6 的数据在 Rangpur 上准备，不在 8×H100 上准备。** 数据处理是 CPU 活，在 $12/小时的 GPU 机器上做太浪费。Rangpur `cpu` 分区作业把原始数据下载到节点本地盘（197 GB）、分词、逐分片上传到对象存储；8×H100 开机后直接拉取。

### 关键认知

**算力买的是模型质量，不是学习收益。** P1–P5 的全部内容——分词器、数据管线、架构实现、数值对齐、训练框架、缩放律、消融——在本地和 Rangpur 上免费完成，那才是项目主体。P6 的 $30 只是把一条已验证的流水线放大跑一次。

### 用竞价实例的前提

竞价便宜 40–50%，但实例随时会被抢占。必须先做到：

1. 每 1000 步存 checkpoint 并**立即同步到对象存储**
2. 启动脚本能自动检测并从最新 checkpoint 恢复（含 dataloader 状态与 RNG）
3. 恢复后的 loss 曲线无跳变

这三条和 Rangpur 的接力续跑是**同一套代码**（见 [09-rangpur.md](09-rangpur.md) §4.2）——在 Rangpur 上跑 P5 时会被反复验证，到 P6 时已经很可靠。

## 六、租机操作要点

1. **先租最小的确认环境**：1 卡跑 30 分钟，确认 CUDA 版本、`torch.compile` 能过、数据能读、W&B 能连
2. **数据别放在实例本地盘** — 放对象存储（S3/R2/OSS），实例启动时拉取或直接流式读
3. **checkpoint 立刻同步到对象存储** — 实例被抢占是常态，不是意外
4. **用 tmux / nohup** — SSH 断了训练不能停
5. **算好再开机** — 开机前用公式估一遍时间，跑起来 10 分钟内核对实际吞吐与估算是否一致，差太多立刻停机排查
6. **监控要能推到手机** — W&B alert 或简单的 webhook，半夜炸了要能知道

## 七、MFU 上不去的排查顺序

1. dataloader 打不满 GPU（看 `step_time` 里的等待占比）→ 加 worker、预取、把数据放本地 NVMe
2. 没开 `torch.compile` 或被 graph break → `TORCH_LOGS=graph_breaks` 查
3. 没用 FlashAttention → 确认走了 `F.scaled_dot_product_attention` 的 flash 后端
4. batch 太小 → 增大 micro-batch 直到显存打满，再用梯度累积凑全局 batch
5. 维度不是 128 的倍数 → tensor core 对齐（本项目 d=1024、ffn=2816 已对齐）
6. 通信瓶颈（多卡）→ 检查是否 NVLink，`NCCL_DEBUG=INFO` 看拓扑
7. 梯度检查点开太多 → 250M 单卡显存够，能关就关（省 30% 时间）
